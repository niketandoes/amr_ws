Phase 1: Simulation World and Single-Robot Baseline

* Build a Gazebo warehouse world containing aisles and shelving.


* Ensure standard aisle widths are maintained, but intentionally construct at least one narrow choke point or 4-way intersection.


* Size the choke point clearance so that it forces a bottleneck where multiple robots cannot pass simultaneously.


* Spawn one differential-drive AMR using URDF or SDF format.


* Equip the AMR with a LiDAR plugin that publishes to the /scan topic.


* Bring up the Nav2 navigation stack specifically for that single robot.


* Configure the local and global costmaps to process the LiDAR data for basic obstacle avoidance.


* Send navigation goals to confirm the single robot can autonomously path-plan point-to-point through the engineered choke point.


* Verify success when this single robot navigates the full warehouse world completely unattended with zero manual intervention.



Phase 2: Multi-Robot Spawn and the Naive Baseline

* Spawn a minimum of 3 separate AMR instances within the same Gazebo world.


* Place each robot under its own dedicated ROS 2 namespace, such as /robot1, /robot2, and /robot3.


* Ensure topics and TF frames do not collide across robots.


* Launch an independent Nav2 stack for each robot instance.


* Use this independent setup to accurately simulate one edge computer per robot, rather than a centralized brain controlling multiple bodies.


* Do not add any peer-to-peer coordination logic during this phase.


* Assign tasks that deliberately force the robots' paths to overlap at the narrow choke point.


* Observe and record the default behavior, noting if the robots experience physical collisions, permanent deadlocks, or a default stop-and-wait behavior driven by Nav2's local costmap.


* Log the timestamps of this uncoordinated run, as this forms the exact benchmark baseline required for Phase 7.



Phase 3: Decentralized Peer-to-Peer Intent Sharing

* Configure each robot to publish its own current pose and current velocity.


* Extract the next 2 to 3 planned waypoints from the robot's active path and include them in the broadcast.


* Publish this payload on a scoped topic like /fleet/intent.


* Tag every published message with the specific robot ID and a timestamp.


* Configure every robot to subscribe to the intent topics of all its peers.


* Ensure there is no central broker or relay node in the loop.


* Rely entirely on ROS 2's native DDS transport to form a flat, peer-to-peer mesh network.


* Implement a fixed-rate heartbeat as the simplest publish trigger.


* Optionally upgrade to an event-triggered publish rate later, which triggers only when the plan deviates beyond a threshold to save bandwidth.


* Verify success by checking each robot's terminal to confirm it is receiving live intents directly from peers without a central node.



Phase 4: Conflict Detection and Negotiation

* Execute a conflict check at every control cycle for each robot.


* Compare the robot's own upcoming path against the shared intents received from peers.


* Check for spatial-temporal overlap using a simple bounding-radius combined with a time-window.


* Trigger a negotiation step immediately upon detecting a predicted conflict.


* Build a deterministic fallback rule first, such as forcing the robot with the lower ID to yield, or granting right-of-way to whoever claimed the shared zone first.


* Use this deterministic rule to eliminate deadlocks and establish a defensible algorithmic baseline.


* Layer in the edge-AI component by training a small Multi-Layer Perceptron (MLP).


* Format the MLP to take the relative pose and velocity of the two conflicting robots as inputs.


* Format the MLP to output a binary decision to either yield or proceed.


* Train this model quickly via imitation learning by using hundreds of simulated conflict scenarios generated by the deterministic fallback rule as the training labels.


* Command the yielding robot to pause or calculate a local detour.


* Command the proceeding robot to continue its path uninterrupted.


* Verify success by running repeated trials and achieving zero collisions at the choke point without any symmetric stalling or "robot dance" behavior.



Phase 5: Blocked-Aisle Detection and Decentralized Task Re-routing

* Trigger a mid-run blockage by either spawning a static obstacle or manually flagging a robot as blocked.


* Program the blocked robot to broadcast a "task-blocked" message.


* Include the specific task ID and the pickup location in this broadcast.


* Ensure this message goes directly to peers, with no central dispatcher involved.


* Program idle or available peers to receive this message and independently compute their own estimated cost to reach the task's pickup point.


* Command the peers to reply with a bid based on their calculated cost.


* Award the task to the robot that submits the lowest bid, following the Contract Net Protocol pattern.


* Instruct the originally blocked robot to re-plan its route around the obstacle to finish remaining work, or switch to an idle state if its queue is empty.


* Verify success by observing an automatic task handoff triggered by a blockage with zero manual intervention.



Phase 6: Fleet Dashboard

* Utilize the rosbridge_websocket node from the rosbridge_suite package.


* Expose the local ROS 2 topics over a plain WebSocket running on the same machine as the simulation.


* Avoid building a custom backend REST layer.


* Publish odometry data natively via each robot's /robotN/odom topic.


* Create a lightweight simulated topic for battery state (/robotN/battery_state), draining it based on distance traveled or active time since Gazebo lacks real battery physics.


* Create a status topic (/robotN/status) indicating if the robot is idle, moving, negotiating, or blocked.


* Build a single-page frontend UI using the roslibjs library.


* Connect the frontend straight to the rosbridge WebSocket at ws://localhost:9090.


* Subscribe directly to each robot's odometry, battery, and status topics from the frontend.


* Render the live positions on a 2D canvas or a Leaflet map overlay of the warehouse layout.


* Display a battery bar and a status badge for each robot that updates live as messages stream in.


* Verify success when the dashboard successfully shows all 3 robots' live positions and telemetry updating in real-time.



Phase 7: Benchmark Against the Success Criteria

* Design a fixed, repeatable test scenario featuring a specific set of pickup and dropoff tasks.


* Engineer this task set to definitively force overlapping paths through the choke point on every run.


* Execute Condition A (the control) by re-running the Phase 2 uncoordinated baseline, where robots fully halt and wait their turn upon detecting a conflict.


* Execute Condition B by running the full decentralized coordination stack developed in Phases 3 through 5.


* Log the total fleet task-completion time, measured from the start of the first task to the finish of the last task.


* Log the total collision count per run.


* Log the exact negotiation latency incurred per conflict.


* Repeat both Condition A and Condition B multiple times to generate credible evidence.


* Compute the percentage time reduction of Condition B versus Condition A.


* Confirm the final results meet the target criteria of a 20 percent or greater reduction in time and exactly zero collisions.


* If targets are missed, iterate on tuning the conflict-detection threshold, the yield rule, or negotiation timing rather than building new features.
